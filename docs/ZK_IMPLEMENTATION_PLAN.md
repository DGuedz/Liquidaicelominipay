# LiquidAI: ZK-Shielded Treasury Implementation Plan

This document outlines the step-by-step engineering roadmap to transform LiquidAI from an account-based AI agent into a **ZK-encrypted UTXO state machine** on the Celo network. 

This is the technical execution plan for the "Digital Offshore" thesis, combining Zero-Knowledge proofs, Agent-to-Agent (A2A) Dark Pools, and compliant Fiat Off-ramps (PIX).

---

## Phase 1: Cryptographic Foundation (The ZK Circuits)
*Objective: Build the mathematical proofs required to process encrypted UTXO notes without revealing their contents to the Celo EVM.*

### 1.1. Circuit Language Selection
- **Stack:** We will use **Noir** (by Aztec) or **Circom**. Noir is preferred for its Rust-like syntax and robust EVM verifier generation.
- **Hash Function:** Poseidon hash (highly optimized for ZK circuits) will be used to hash UTXO notes and build the Merkle Tree.

### 1.2. The Core Circuits
We need to write three main ZK circuits:
1. **`Shield.nr`**: Proves a public token deposit corresponds to a newly minted private UTXO Commitment.
2. **`Transfer.nr` (A2A Dark Pool)**: Proves that the sum of input notes equals the sum of output notes + relayer fees. It verifies the ownership of inputs and outputs valid Nullifiers (to prevent double-spending).
3. **`Unshield.nr`**: Proves the destruction of a UTXO note to release public tokens to a designated address (e.g., the PIX Gateway).

### 1.3. Proof of Innocence (PoI) Integration
- Integrate a secondary circuit that verifies the user's UTXO history against a cryptographic accumulator of "clean" addresses, without revealing the user's specific address.

## Phase 2: Smart Contract Architecture (The On-Chain Vault)
*Objective: Deploy the Solidity contracts on Celo that will act as the "Public Computer" verifying the "Private Computer's" math.*

### 2.1. `LiquidShield.sol` (The Main Vault)
- Holds all public ERC20 tokens (cUSD, USDm, BRLm, EURm).
- Maintains the incremental Merkle Tree of all UTXO Commitments.
- Maintains the mapping of used Nullifiers (preventing double-spending).

### 2.2. `ZKVerifier.sol`
- Auto-generated from the Noir/Circom circuits.
- `LiquidShield.sol` calls this contract to validate the math before executing any state transition.

### 2.3. `DeFiAdaptor.sol` (The Yield Shield)
- **The Gap Solved:** Allows shielded funds to earn yield without unmasking the user.
- **Implementation:** 
  1. Receives an atomic `unshieldAndCall` instruction.
  2. Deposits the unshielded USDm into Mento V3 or Aave.
  3. Receives yield-bearing tokens (aUSDm).
  4. Immediately calls `shield()` to convert aUSDm back into a private UTXO note for the user.
  5. The EVM only sees the Adaptor contract interacting with Aave.

## Phase 3: Relayer Network & Gas Abstraction
*Objective: Ensure users never pay CELO gas from their public wallets, completely severing on-chain metadata correlation.*

### 3.1. The Broadcaster Node (Node.js/Go)
- A decentralized off-chain service that listens for `Shielded Intents` generated by the LiquidAI frontend.
- **Intent Structure:** `{ ZK_Proof, Relayer_Fee_Amount, Encrypted_Payload }`

### 3.2. Gas Sponsoring Flow
1. User's MiniPay app generates the ZK Proof locally.
2. App sends the proof to the Broadcaster via a standard HTTPS API.
3. Broadcaster wraps the proof in a Celo transaction and pays the network Gas fee in CELO.
4. `LiquidShield.sol` verifies the proof. As part of the valid proof, it mints a small UTXO fee note directly to the Broadcaster's shielded balance.
5. **Result:** User pays gas in USDm invisibly; Broadcaster profits the spread.

## Phase 4: The PIX "Last Mile" (`unshieldAndCall`)
*Objective: Allow a user to send money to a real-world bank account (PIX) without exposing their crypto wallet balance or history.*

### 4.1. The `unshieldAndCall` Mechanism
- Standard unshielding sends funds to the user's public Celo address. We will bypass this.
- The ZK circuit will be modified to accept a `public_calldata` parameter.
- The user creates a proof that destroys 100 BRLm notes and instructs the vault to send the 100 BRLm **directly to the Transfero/Belo Smart Contract Gateway**.

### 4.2. Encrypted PIX Metadata
- The user encrypts their PIX Key (CPF/Email) using the public key of the Transfero/Belo gateway.
- This encrypted payload is passed via the `unshieldAndCall` transaction.
- **Result:** The Celo network sees `LiquidShield` sending 100 BRLm to `TransferoGateway` with an encrypted hex string. Only Transfero can decrypt the string, read the CPF, and fire the PIX. The user's identity is known *only* to the compliant gateway, not to the blockchain.

## Phase 5: Client-Side Engine (MiniPay DApp)
*Objective: Make this deep cryptography invisible to the end-user.*

### 5.1. WASM Prover
- Compile the Noir/Circom provers to WebAssembly (WASM).
- The MiniPay React app will download the WASM file and generate the ZK Proofs locally on the user's smartphone (takes ~1-3 seconds on modern devices).

### 5.2. AI Agent Orchestration
- The LiquidAI Agent (`chat-service.mjs`) translates natural language into these complex intents.
- *User:* "Send 50 BRL via PIX to my mom, but use my shielded balance."
- *Agent:* Constructs the payload -> Prompts WASM to generate the proof -> Sends to Relayer -> Broadcaster executes `unshieldAndCall`.
